Event log {{ rail.count }} entries, never edited
The payment system’s own audit trail. The real code writes it as it runs; entries are only ever added, never changed or removed. What’s in it: proposals and approvals, every request that can move or reserve money (logged by its sender just before the call) and the answer it got, money reserved and sent, settlement at the bank, state changes, refunds and cancellations, standing terms published or refused at the registry, and what the shopping agent showed or was refused. What’s not: behind-the-scenes checks (signature checks, the split, registry reads), steps the explorer works out itself, and the setup before the coordinator starts (accounts, keys, the employer’s allowance) — those live only in the Steps list. Several logs in one: the coordinator, the registry, each provider, the digital-euro ledger, bank transfers and the shopping agent each write their own entries. Here they share one numbering; in production each party keeps its own log, and this view would be combined from them. Fingerprint: a short hash of the whole log. The same starting world and the same code always give the same fingerprint, so a match shows this page runs the real code. The four AI shopper runs match the test suite byte-for-byte. Only this run: every entry was written by this run, in your browser. Nothing is imported. Source{{ l.label }} Grouped by the stage that caused them. Stages
A stage starts when someone takes an action, such as approving or paying. Where money can move, each step is one interaction: one party asks another, and the answer comes back. Calls the receiver makes before it can answer are numbered inside the step — 8.1, 8.2… — straight from the log: every request carries an ID and names the request that caused it. A request with no answer yet stays open; it is never shown as a failure, because a missing answer doesn’t prove nothing happened.
