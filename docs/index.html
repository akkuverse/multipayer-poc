One purchase.
Two payers.
Two kinds of authority.

A deterministic coordinator for a merchant purchase funded by two payers with different authority — an employee approving a specific purchase, an employer contributing under a bounded mandate. Built to explore co-funded digital euro payments.

Not a payment system. Everything runs locally against simulated settlement ledgers with synthetic actors and amounts — no personal data, no real money, no network calls. By Akku Labs.

The reference case

The €13 lunch

An employee buys lunch for €13. Their employer subsidises one meal per working day. The coordinator splits the purchase into two legs, each under its own authority, and completes only when both settle.

Merchant receives the full amount — a business wallet holds nothing. One purchase, one completion state, two contributions.

The same coordinator also runs bill splits, group purchases and one-payer multi-payee orders. All amounts are integer euro cents. Benefit conditions live in the application — never in the money.

Signed authority

Identifiers are born bound

Approvals and mandates are Ed25519 signatures over canonical JSON. Publication is the trust decision: the registry schema-checks every record, verifies the signature against the key bound to the party it names and accepts only the next version — a rejected write can never displace the terms already in force. The coordinator still verifies at every use and fails closed.

The name tag

A ref is a name, not the mandate

A purchase carries only the mandate's name — mandateRef — looked up fresh at every use, so a changed or revoked mandate takes effect at initiation. That indirection is the feature; it is also the attack surface, so a write only lands when it is signed by the ref's owner and carries the ref's next version — a stale or foreign revision is rejected at publish and the accepted record stays in force.

The pin

First come, first served — permanently

Whoever publishes a ref first owns that name. A later publish under the same ref naming a different employerId is rejected: mandate-1 can only ever resolve to employer-1's authority. Versions change; ownership doesn't.

Two questions, two mechanisms

The signature answers "is this mandate really from who it claims to be?" The pin answers "does this name still mean what it meant yesterday?" Both are enforced at publish: without the pin an attacker could post their own mandate under a victim's ref mid-flight — the signature verifies, but the money would route through the wrong party's authority and every leg's authorityRef audit link would break — and a forged publish claiming the same employer passes the pin but fails signature verification. Either way the write is rejected and the accepted terms stand. The coordinator then re-verifies the retained signature at every use, so a record corrupted after acceptance can only deny funding, never create it. Fail closed.

The same pattern guards the keys: keyId → holder. A key means only "the party it was registered to" — a perfectly valid signature by someone else's key is rejected.

Purchase lifecycle

Completion is earned, not assumed

State is derived only from authoritative settlement status. A timeout stays pending; partial commitment stays visibly outstanding until resolved.

draft→ awaiting_approvals→ ready→ pending→ completed
failed · nothing committed recovery_required · committed amount stays visible cancelled · all obligations resolved

Returns carry their own status and never erase the original settlement record.

Two settlement modes, one fixture set

Reserve-all, then commit — with compensation

Atomic

Every leg's hold is reserved first; legs then commit across two ledgers. A conclusive failure releases holds, restores funding and compensates whatever already committed — not a cross-ledger atomic step.

S06: one leg fails → failed · no money moved
Baseline on existing rails

Independent

Each leg is a separate payment — one can settle while the other fails, leaving committed money to reconcile and return.

S05: same failure → recovery_required → refunded → cancelled

Agent protocols, kept at arm's length

The coordinator implements no agent protocol, but its authority objects are designed to map onto them — chiefly AP2, whose mandates solve the same problem for a single payer. The gap: no current protocol covers a co-payer's mandate contributing to someone else's purchase. Where agents do appear, the boundary is fixed — agents read and explain; deterministic code decides amounts and eligibility; only authorised parties approve spending.
